# Phase 6 — Withdrawal Flow and Webhooks

**Goal**: Interac withdrawal payouts, status checks, and the `payout.interac.completed` webhook.

**Definition of Done**: This phase is complete when `make test` passes successfully.

## Deliverables

- `internal/storage/interface.go` extended: `CreatePayout`, `GetPayoutByChiRef`, `GetPayoutByIssueID`, `UpdatePayoutStatus`
- `internal/storage/memory.go` updated
- `internal/handler/payout.go`:
  - `POST /v0.2.4/payouts/interac` — validates `debitCurrency`, `interacs` non-empty; validates sub-account exists; creates a `Payout` per interac entry; enqueues `payout.interac.completed` webhook
  - `POST /v0.2.4/payouts/status` — validates `chiRef` required; returns payout by chiRef
- Response shape for payout initiation: `{ "data": [{ "id", "issueID", "amount", "fee", "debitCurrency", "type", "chiref" }] }`
- Enqueued withdrawal webhook body: `{ "eventType": "payout.interac.completed", "issueID": "...", "status": "completed", "amount": "...", "meta": { "issuer": "<subAccountID>", "amount": N, "currency": "CAD", "paymentType": "interac" } }`

## Feature File

`features/withdrawals_and_webhooks.feature`

## Dependencies

- Phases 0–5 must be complete and green

## Test-Driven Development Notes

1. **Red**: Run feature scenarios for withdrawal initiation and status checks. Expect handler not found errors.
2. **Green**:
   - Implement storage methods for payout CRUD.
   - Implement handlers with validation.
   - Enqueue `payout.interac.completed` webhook via the job queue from Phase 5.
3. **Refactor**:
   - The `issueID` format `{subAccountID}_{uuid}` is now used by both payments (Phase 4) and payouts (this phase) — confirm it is generated by a single utility function.
   - Payout status updates from webhook delivery must be reflected in subsequent `payouts/status` calls. Consider whether to update status automatically on webhook enqueue, or wait for explicit callback.
   - Run all previous feature scenarios.
